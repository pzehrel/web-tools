# Web UI redesign implementation specification

Type: spec
Status: ready-for-agent
Labels: ready-for-agent
Date: 2026-10-20
Canonical language: English
Test boundary: confirmed by the user on 2026-10-20

## Problem Statement

The existing tool interfaces do not provide the compact, consistent workspace needed for frequent development and design work. Navigation, spacing, controls, feedback and canvas organization need a complete UI redesign. Earlier simplified prototypes also made existing capabilities difficult to identify, creating a risk of losing important functionality during implementation.

The user has completed review of the current F prototype. Production implementation must preserve the complete behavior of the four public tools while adopting the approved layouts and shared semantic color system. The reviewed prototype is a design reference, not the production implementation or evidence that all runtime behavior has passed acceptance.

## Solution

Implement the reviewed home, URL and QR tool, frame-animation tool, Lottie preview and nine-patch tool as production interfaces. Use compact controls, direct navigation, visible canvases, task-specific floating controls and consistent light/dark semantic colors. Preserve existing parsing, image processing, rendering, exports, records and compatibility behavior.

The home and tool switcher expose only the four public tools. CSS shine and font toolkit remain deferred and have no visible navigation entries; their existing direct routes and functionality remain. Keep the application browser-based, retain the current storage and SSG architecture, and avoid promotional emphasis on data location or upload behavior.

## Implementation Decisions

### Scope and source of truth

- Implement the home, shared interface and four public tools: URL and QR, frame animation, Lottie preview and nine-patch. Use “URL 与二维码” consistently in the Chinese interface. Keep the approved F home ordering and direct-entry organization.
- The final reviewed F behavior and the feature-retention criteria jointly define the result. Historical “missing” prototype coverage is not permission to omit functionality. Preserve U01–U25, F01–F20, L01–L20, N01–N29 and G01–G09, subject only to the explicit overrides below: 103 existing groups in this implementation scope.
- D01–D12 name reviewed interface decisions, not additional historical feature groups. The 115 stories cover both kinds of requirement.
- Reuse existing parsing, QR codecs, image/crop calculations, animation engines, atlas optimization, archives, resource metrics and storage contracts. Build maintainable production components from these contracts; retain the prototype as a separate design reference.
- Preserve unrelated user changes. This specification does not authorize a release, deployment, automatic commit or destructive cleanup.

### Shared interface and color

- Keep compact page headers, recognizable titles, left-side return navigation, a public-only tool switcher, correct GitHub icon/link and three-way theme selection. Navigation is not a persistent management sidebar.
- Keep navigation menus above floating canvas controls and active modals above the header. Align header/canvas controls and bound popovers to the viewport so controls do not overlap or become obscured.
- Use existing semantic component conventions for primary, secondary, outline, ghost and destructive actions. Icon-only actions have no visible border; hover, selection, disabled and focus states remain visible. Theme actions remain equal squares with centered icons and soft selected fills.
- Promote the reviewed blue-primary, soft-blue-secondary, green-success, red-error, amber-warning and cyan-blue-information palette into the production light/dark theme. Keep raw palette values centralized and component styling semantic. The final interface must not depend on a development-only palette gate.
- Keep status text/icons alongside hue. Confirmed copy feedback may briefly switch a primary action to a readable success fill. Classify outcomes from explicit state, not translated message substrings. Distinguish nonfatal warnings and informational no-op results from failures.
- Preserve compact controls and the absence of decorative shadows/hover displacement. The reviewed semantic color, compact layout and floating task-panel rules supersede conflicting old monochrome, single-hue and spacious-form rules for the redesigned public interface. Record the reconciled production design guidance during implementation.
- Keep desktop working panels narrow, approximately the reviewed 240-pixel parameter width, with internal scrolling where needed. Mobile must retain imports, core parameters, preview, output and record access through the reviewed tabs/stacking; precise slicing and multi-frame ordering remain desktop-first, not removed on phones.

### URL and QR layout and exports

- On desktop, input and QR panels share the first row and stretch to equal height, with the QR centered. The editable tree spans the second row; records span the third. At compact/mobile widths, stack the complete sections without page-wide horizontal overflow.
- Preserve the actual recursive editable tree and its ancestor connectors; do not add a separate flat parsed-result summary. Tightening applies to item spacing, not the title or outer section: ordinary rows have the reviewed 20-pixel minimum, root rows 24 pixels and editing rows may grow. Long values wrap or remain reachable in the tree's scrolling region; controls remain usable.
- Keep original-input copying distinct from serialized root/subtree copying. Keep all insertion locations, invalid-drop protection, deletion confirmation, variables and conditional code copying.
- Generate the existing 320-pixel, correction-level-L QR PNG with 400-millisecond debounce and stale-result protection. Page download is pure QR. The enlarged dialog directly downloads the existing combined image for URL content; plain text falls back to pure QR. Remove the download dropdown and its menu-specific close behavior by explicit user decision, while retaining availability, busy protection, retryable errors and both export formats.
- Preserve combined-image output geometry: 1400-pixel width, 500-pixel QR, wrapped tree text, a 300-line drawing limit and an omission indication. Keep existing output naming and encoding behavior.
- Save always creates a new snapshot. Updating a selected record remains explicit; typing does not overwrite saved content. Keep original naming, preview, selection/deselection and rename/delete semantics.
- Preserve current, old-text and bare share hashes, debounced history replacement and clearing. Start empty when no share content exists; the OAuth example is explicit.

### Frame-animation workspace

- Use the reviewed narrow left parameter panel, main canvas, full-width bottom sequence and a short floating playback/progress control immediately above it. The sequence occupies the left-panel area too; its collapse releases canvas space and controls stay reachable.
- Keep playback progress visible and seekable. Seeking pauses and may inspect any selected frame without rewriting the configured playback/export range; resumed playback obeys that range.
- Explicit F06 override: omit playback-following thumbnail highlighting and automatic following. Keep user selection, focus, drag targets, thumbnails, metadata, sorting and click-to-pause/seek. The current frame remains identifiable through the progress controls.
- Preserve append/natural-sort rules, selection, common-transparent-edge cropping and complete export options. Keep PNG sprite output at source-derived resolution, centered smaller frames and linked rows/columns; preserve CSS/Less/SCSS generation. No GIF/video exporter is introduced.
- Preserve defaults and bounds: 12 FPS initially, 1–60 FPS slider, 1–120 numeric input including duration-derived fractions, inclusive playback/export range, forward/reverse/ping-pong and infinite or 1–999 loops. Keep existing crop alpha thresholds and reset/error behavior.

### Lottie workspace

- Use the reviewed narrow left task panel with atlas optimization, playback settings and project-record tabs. Resource comparison and the primary ZIP export remain reachable below the task content. Switching tabs preserves edits and focus behavior.
- Keep project import/metadata and viewing controls organized in the shared top toolbar. Keep the short playback control on the canvas and the atlas in a separate floating preview. Scrollable asset messages belong in the parameter-panel footer; failure details expand appropriately and mobile has a discoverable message entry.
- Preserve ZIP/directory import constraints, all existing asset resolution and both rendering libraries/renderers. Do not add automatic remote-image retrieval or unsupported loose JSON import.
- Preserve fractional seeking at 0.01-frame steps, the existing speed presets, direction, loop and fitting modes. Seeking pauses. Main and atlas views remain independent.
- Preserve packing controls/defaults: 1024/2048/4096 maximum size; padding 0–32, default 2; extrusion 0–8, default 1; rotation off, trimming on, deduplication on; advanced power-of-two and square off; alpha threshold 0–255, default 1. Keep animated-image exclusions and increased-resource warnings.
- Preview the current valid optimization result, use original assets while rebuilding or disabled, and export the existing rewritten animation, numbered atlases and required original assets as a valid ZIP. Resource metrics must describe the same result, with estimated memory clearly distinguished from measured file bytes.

### Nine-patch workspace

- Keep the reviewed narrow left panel and visible source canvas. Parameter order is slice margins, frequent center cropping, then rendering settings. CSS and records remain available; copy, save and cropped-PNG actions remain reachable.
- Use an overlaid stretch-preview HUD, initially in the lower-right working area, with title dragging, eight outer resizing handles, bounded positioning and its own reset. Support keyboard movement/resizing, pointer end/cancel/lost-capture cleanup and viewport clamping.
- HUD geometry changes the observation window only. Preserve independent inner logical stretch dimensions of 96–720 by 64–480 pixels, eight logical sizing handles and corner keyboard increments of 8/Shift-40 pixels. HUD movement/resizing uses the reviewed 8/Shift-32-pixel keyboard steps. Keep HUD geometry and view transforms out of export and saved parameter data.
- Keep source-view reset, preview-view reset and HUD reset clearly distinct. Preserve source-pixel cut-line dragging and keyboard increments of 1/Shift-10 pixels, invalid-edge clamping, image-derived defaults and the existing automatic analysis behavior.
- Preserve bound/unbound widths, 0–200-pixel independent widths, 0–100-pixel outset, fill and independent stretch/repeat/round/space axes. Preserve both-axis/X/Y center cropping and exact 1:1 PNG output. Center-crop overlays and tiling warnings remain visible.
- Preserve the existing source-based border-image renderer and longhand/shorthand CSS generator. Center-crop output is a separate pixel export; do not claim that the renderer already uses a regenerated cropped bitmap. CSS is the existing callable nine-patch code format; no SCSS/Less/Tailwind generator is added by inference from old metadata.

### Data, runtime and compatibility

- Production interfaces continue using the existing ToolStore, IndexedDB identities, payloads, Blob archives, metadata normalization and existing legacy URL/QR conversion. Do not use the disposable prototype database or migrate its records into production. This is preservation of existing compatibility, not a new storage schema or backend migration.
- Keep existing tool-specific record behavior: URL explicit snapshots/update and confirmations; frame/Lottie named full-project archives; nine-patch source bytes and parameter restoration with targeted deletion. Do not silently add destructive confirmations, autosave or new persistence fields that change these contracts.
- Maintain three-way theme persistence and pre-paint application, object-URL cleanup, asynchronous result ownership and the existing busy guards. View backgrounds, zoom/pan, HUD geometry and source-boundary visibility must not modify output pixels or export parameters except for the already defined pixel-style output setting.
- Preserve explicit route identities, legacy redirect/fallback behavior, SSG hydration-data alignment, per-route SEO and existing browser/Safari web-app metadata. Keep the router compatibility shim and browser-only storage hydration guards.
- The final production interface has no prototype switcher, variant dependency, disposable-record adapter or development-only theme requirement. Retain reproducible prototype references separately without overwriting unrelated working changes.

## Testing Decisions

### Confirmed test boundary

The user confirmed the following boundary on 2026-10-20: test primarily through the actual production pages for input, editing, preview, download, records and refresh; reuse existing parser, stage and record tests; additionally verify SSG hydration, legacy-record compatibility, light/dark themes and phone operation.

Use one highest-level acceptance seam: the product page in a browser, using real fixtures, controls, exported artifacts and persisted records. Exercise each tool through this seam rather than building a parallel mocked UI or exposing new engine APIs for testing. Existing focused module tests remain useful below it.

### Test quality and prior art

- Assert external behavior and user-visible state transitions. Do not assert private hook state, CSS-class strings, copied prototype handlers or incidental component hierarchy.
- Reuse existing URL parse/serialize/tree-movement tests, stage fit/zoom tests, legacy-record parsing/conversion tests, frame/Lottie archive round trips, Lottie asset-resolution/animated-image/resource-metric tests and nine-patch slice-bound tests.
- A repository browser acceptance suite is not yet established. Reuse available browser automation tooling where practical; add a small product-page harness only if required. A new public processing interface solely to make tests easy is not part of this plan.
- Use isolated acceptance storage and deliberately seeded legacy fixtures. Never clear or mutate the user's actual saved records. Reload and old-record tests must exercise the real production storage contract, not the prototype adapter.
- Compare exports by decoding the PNG, inspecting dimensions/pixels, reading generated code and unpacking project archives as appropriate. Button activation and filename presence alone do not prove export correctness.

## Out of Scope

- Redesigning or newly reviewing CSS shine and font toolkit, exposing hidden navigation entries, or deleting their existing direct-route functionality.
- New tools, new import/export formats, GIF/video output, new nine-patch code generators or automatic fetching of remote Lottie assets.
- Backend/admin work, accounts, authentication, cloud synchronization, new HTTP storage contracts or a new database schema/migration system. Existing local legacy-record compatibility remains in scope.
- Desktop wrapping, a framework/router/build-system migration, an offline service worker or an expanded installation promise.
- New analytics, banners or promotional emphasis on local processing, data location or non-upload behavior.
- Unrelated cleanup, rewriting processing engines for styling, automatic publication/release/deployment, or overwriting existing user changes.
